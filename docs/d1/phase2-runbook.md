# Phase 2 runbook: users, auth and user data on D1

This is how the user data is copied to D1 and checked, and where Phase 2
stands. The plan is
[coptic-vine-d1-plan.md](../coptic-vine-d1-plan.md#5-phase-2-users-and-auth-after-phase-1),
and the inventory is [phase2-inventory.md](phase2-inventory.md).

**Decisions (20 Oct 2026):**

- Better Auth on Workers and D1, with email and password, and Google.
- Sign in with Apple comes later, once there's an Apple Developer account.
- Emails go through Cloudflare Email Service.
- There is **one cutover** for auth and all the user data together.
- Until then, Supabase stays the master and is only read.

## What is where

| Piece | Where |
|---|---|
| Sign-in tables | `"auth.users"` (Supabase's user ids and metadata), `"auth.sessions"`, `"auth.accounts"` and `"auth.verifications"`, in migration `0006_auth.sql`. The migration is hand-written, in Better Auth's shape with snake_case columns. |
| User tables | 73 tables in `creator`, `learning`, `media`, `music`, `private` and `public`, in migration `0007_user_schema.sql`. It is generated by `workers/api/scripts/gen-schema.ts` from the catalog snapshot `workers/api/schema/pg-catalog-users.json`. |
| Migrations | One history for the `copticvine` database, in `workers/content-api/migrations`. |
| Worker | `workers/api` (`cv-api`), for `https://api.copticvine.ca`: sign-in now, and the user-data API next. |

**How values are stored:**

- **Timestamps.** Every timestamp is stored as Supabase's REST API prints it,
  always in UTC, such as `2026-10-20T19:52:43.123456+00:00`. That keeps API
  answers identical, and string order is time order.
- **CHECK constraints.**
  - Each `jsonb`, `text[]`, date and timestamp column has a CHECK on its
    shape.
  - The Postgres CHECKs are translated, with regular expressions turned
    into GLOB.
  - D1 refuses LIKE and GLOB patterns over 50 bytes, so the long patterns
    are split into `substr` checks. A test keeps them under the limit.
- **Defaults.** `now()` and `gen_random_uuid()` have SQLite equivalents.
  `auth.uid()` defaults have none, because the Worker always writes the
  signed-in user.
- **Triggers.**
  - The 50 `updated_at` triggers are SQLite triggers.
  - The other 37 (search index refresh, notifications, artwork, release
    rules, artist and cantor syncing) are listed per table in
    `workers/api/schema/user-tables.json`. They are SQLite triggers too, in
    migration `0009` (see "Triggers and writes" below).
  - One CHECK reads today's date (a release date at most a year ahead), so
    the Worker enforces it too.
- **Not copied.**
  - `media.search_documents.search_vector`, a tsvector column; search moves
    to the Worker.
  - The trigram indexes.

## Copying the user data

The export holds personal data: emails and password hashes. Keep it out of
the repository, and delete it once it has been loaded.

```sh
cd workers/api
npm run export-sql            # the read-only export; run it in the Supabase SQL editor or MCP, save the result
npm run import -- --from <saved result>            # into the remote D1 (--local for wrangler dev)
npm run verify -- --print-pg-sql                   # the read-only checksum query; run it the same way
npm run verify -- --pg <saved checksums>           # every table's SHA-256 in D1 against Postgres's
```

**What the import does:**

- It checks every value first: type, NOT NULL, timestamp form, and JSON.
- It replaces the user tables and sign-in tables in one D1 import, which
  applies all of it or none.
- Tables load parents first. D1's remote import checks foreign keys row by
  row; it doesn't honour `PRAGMA defer_foreign_keys`. So the columns that
  close the two cycles (`owner_creator_account_id` on artists and media
  assets) and `media.submission_items.replaces_item_id` are loaded as NULL,
  then filled in once every row exists. Each row's `updated_at` is put back
  after that update, so the trigger's stamp doesn't change the data.

**How the sign-in accounts carry over:**

- Supabase's email identity becomes a `credential` account, holding the
  existing bcrypt hash. The Worker accepts those hashes, and new passwords
  get Better Auth's own hash.
- A Google identity becomes a `google` account, keyed by Google's subject id.
- Sessions aren't copied. Everyone signs in again once, at the cutover.

## Sign-in (`workers/api`, Better Auth)

- **Endpoints.** Everything is under `/auth`: `sign-up/email`,
  `sign-in/email`, `sign-in/social`, `get-session`, `sign-out`,
  `request-password-reset`, `reset-password`, `change-password`,
  `change-email` and `update-user`.
- **Accounts.**
  - Users keep their Supabase ids.
  - The passwords carried over are bcrypt hashes, checked as they are; new
    ones get Better Auth's scrypt hash.
  - Email sign-up needs the confirmation email.
  - Google joins an existing account with the same verified email, as
    Supabase did.
- **Sessions.** They last 30 days and are renewed daily while used. The web
  apps use the session cookie (`copticvine.ca` is same-site with
  `api.copticvine.ca`); the native apps use the Expo plugin's stored session,
  or `Authorization: Bearer`.
- **Abuse protection.**
  - Rate limits are kept in D1 (`"auth.rate_limits"`, migration 0008), per
    address.
  - CORS and redirects only for the origins in `TRUSTED_ORIGINS`.
- **The D1 connector** (`src/auth/adapter.ts`). It builds every name with
  `t()` and `col()`, and stores dates in the user data's timestamp form. For
  text matching it uses `instr`/`substr` rather than LIKE, which keeps clear
  of D1's 50-byte pattern limit.
- **Tests.** `npm test` runs each flow end to end on the real tables in
  SQLite, with the emails kept in an outbox.
- **Locally.** `npm run dev` serves on `http://localhost:8790` against the
  local D1, with the emails kept in memory. It reads `.dev.vars`, made from
  `.dev.vars.example`.

   Email Sending > Onboard Domain and pick `copticvine.ca`. The DNS records

   - `openssl rand -base64 32 | npx wrangler secret put BETTER_AUTH_SECRET`
   - then `npm run deploy` in `workers/api`

**Why it isn't live yet.** Until the cutover, a sign-up or password reset
made here would be wiped by the final import, and the apps still sign in with
Supabase.

## The user-data API (`/rest/v1` on `cv-api`)

**How it answers.** It answers the apps' supabase-js calls as Supabase's REST
API does, so the apps keep their code:

- `POST /rest/v1/rpc/<function>`, in `src/rpc`;
- the six tables the apps use directly, in `src/rest/tables.ts`.

The user always comes from the session. `schema/functions.json`,
generated from the dump, gives each function's parameters, defaults and
types, and Supabase's EXECUTE grants. So calls are matched, arguments are
checked (uuid syntax, enum values) and signed-out calls are refused, all
exactly as PostgREST and Postgres do it.

**Visibility.** Supabase's row-level security is written out as SQL
fragments (`src/rpc/common.ts`): published, or readable by the creator
account or an admin. They are added to every read the original made as the
caller.

**Text order.** Text is sorted the way Supabase sorts it (ICU en-US), and
the oracle collates its text columns the same way.

**How it is checked: the parity oracle.** `tests/lib/oracle.ts` runs
Supabase's own functions, policies and grants in PGlite (Postgres compiled to
WebAssembly). They come from `schema/pg-user-schema.sql`, the structure-only
dump made by `schema/pg-schema-dump.sql` and saved with
`npm run save-schema-dump`.

- The `*.parity.test.ts` tests send the same calls, as the same users, to
  the oracle and to the Worker. The Worker runs on SQLite with the real
  migrations, and its users sign in through Better Auth.
- The answers must match: the data, or the error code and message. Ids and
  server timestamps that each side generates itself are compared as
  placeholders.
- Writes are compared table by table.
- Nothing touches Supabase.

**Production bug found by the oracle: playlist editing.**

- **Since when:** migration `20260921221500_notification_infrastructure.sql` (21 Sept 2026) revoked the signed-in role's USAGE on schema `private`.
- **What breaks:** every SECURITY INVOKER function that calls a `private.*` helper by name now fails with "permission denied for schema private". On Supabase today that means adding, removing and reordering playlist tracks, renaming a playlist and deleting one. Unused creator functions fail too. The last track added to a playlist was on 21 Sept.
- **The Worker:** it implements the working behaviour. The parity tests compare it with Supabase as it was before the revoke (`createOracle({ privateUsage: true })`), and one test records the failure as deployed.
- **On Supabase:** left as it is (Pierre, 21 Oct 2026); only the new database has to work.

**Triggers and writes.**

- **Triggers.** `npm run gen:triggers` writes migration `0009_user_triggers.sql` from `scripts/gen-triggers.ts`: Supabase's triggers as SQLite triggers, so D1 applies them to every write, in the same transaction, whoever writes. The script's header says how each kind maps (BEFORE triggers that change the row, the order triggers fire in, errors with their SQLSTATE).
- **Replica mode.** `"private.replica_mode"` turns every trigger off while it is above 0, as `session_replication_role = replica` does. The import raises it for its whole run.
- **After the write.** Two things Supabase did outside the transaction, the Worker does once the write has committed (`src/db/afterWrites.ts`): rebuild the catalog search index when the catalog changed (the triggers count changes in `"private.search_index_state"`), and wake the media processor when a job is queued (`"private.outbox"`). A cron runs the same step every minute, in case a request missed it.
- **Atomic.** A Supabase function runs in one transaction. D1 has none across statements (only a `db.batch()` is atomic), so:
  - a ported function that can check everything first writes in one batch;
  - one that must read what it wrote (the creator editor's, the admin's) runs in `transaction()` (`src/db/transaction.ts`): migration `0010`'s triggers record the inverse of each of its writes in `"private.undo_log"`, cascades and trigger writes included, and a failure plays them back. The minute cron rolls back any transaction a Worker never finished. Unlike Postgres, other requests can see a transaction's writes before it ends.
  - The tests' D1 stand-in makes batches atomic as D1 does; `tests/transaction.test.ts` checks that a rollback restores every row, and it was also checked on workerd's D1.
- **Checked by** `tests/triggers.parity.test.ts`: the same writes on the oracle and on SQLite, every table compared after each. The search index rebuilt from the real D1 copy matched Supabase's, 103 documents of 103, field by field.
- **Not ported:** `media.search_aliases`' normalization trigger. Nothing writes that table; whatever does must store `normalized_alias` with `normalizeSearchText`.
- **Applied** (`0009`, `0010`) to the local D1. The remote D1 gets them at the cutover, before the final import (which needs `0009`).

**After a change to a Supabase function, until the cutover:**

1. Re-run the dump and `npm run save-schema-dump -- <result>`.
2. Run `npm run gen:functions`. It regenerates `schema/functions.json`, which records each function's parameters, defaults, types and grants.
3. Run the tests; they show what the Worker's port has to follow.

**Search.** `src/rpc/search` computes what Postgres computed for the two
functions: `media.normalize_search_text`, `pg_trgm`'s `similarity`, and each
document's weighted `search_vector`, built per query from its title (A),
subtitle (B) and body (C). The full-text parser, queries and `ts_rank_cd` are
Phase 1's, which now also handle weights.

- `tests/search.parity.test.ts` compares the Worker with the oracle on a
  seeded ASCII catalog. The oracle's collation is C, so it can't judge Arabic
  or Coptic.
- `tests/search.text.test.ts` covers those: Supabase's own answers for
  Arabic, Coptic, Greek and French text, recorded on 20 Oct 2026.
- `npm run search-parity` sends 404 calls to Supabase's functions (anon key,
  read only) and to the port over the local D1, and compares the answers. On
  20 Oct 2026: **404 of 404 match**. In 15 of them, results with the same rank
  and the same title (a release and its title track) come in another order;
  Postgres leaves that order to its plan.
- Still to come with the trigger work: whatever writes `search_documents`
  (`private.refresh_unified_search_index`) and `search_aliases` must store
  `normalized_text` and `normalized_alias` with `normalizeSearchText`.

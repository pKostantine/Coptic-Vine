# Phase 2 runbook: users, auth and user data on D1

This is how the user data is copied to D1 and checked, and where Phase 2
stands. The plan is
[coptic-vine-d1-plan.md](../coptic-vine-d1-plan.md#5-phase-2-users-and-auth-after-phase-1),
and the inventory is [phase2-inventory.md](phase2-inventory.md).

**Decisions (20 Oct 2026):**

- Better Auth on Workers and D1, with email and password, and Google.
- Sign in with Apple comes later, once there's an Apple Developer account.
- Emails go through Cloudflare Email Service.
- There is **one cutover** for auth and all the user data together.
- Until then, Supabase stays the master and is only read.

## What is where

| Piece | Where |
|---|---|
| Sign-in tables | `"auth.users"` (Supabase's user ids and metadata), `"auth.sessions"`, `"auth.accounts"` and `"auth.verifications"`, in migration `0006_auth.sql`. The migration is hand-written, in Better Auth's shape with snake_case columns. |
| User tables | 73 tables in `creator`, `learning`, `media`, `music`, `private` and `public`, in migration `0007_user_schema.sql`. It is generated by `workers/api/scripts/gen-schema.ts` from the catalog snapshot `workers/api/schema/pg-catalog-users.json`. |
| Migrations | One history for the `copticvine` database, in `workers/content-api/migrations`. |
| Worker | `workers/api` (`cv-api`), for `https://api.copticvine.ca`: sign-in now, and the user-data API next. |

**How values are stored:**

- **Timestamps.** Every timestamp is stored as Supabase's REST API prints it,
  always in UTC, such as `2026-10-20T19:52:43.123456+00:00`. That keeps API
  answers identical, and string order is time order.
- **CHECK constraints.**
  - Each `jsonb`, `text[]`, date and timestamp column has a CHECK on its
    shape.
  - The Postgres CHECKs are translated, with regular expressions turned
    into GLOB.
  - D1 refuses LIKE and GLOB patterns over 50 bytes, so the long patterns
    are split into `substr` checks. A test keeps them under the limit.
- **Defaults.** `now()` and `gen_random_uuid()` have SQLite equivalents.
  `auth.uid()` defaults have none, because the Worker always writes the
  signed-in user.
- **Triggers.**
  - The 50 `updated_at` triggers are SQLite triggers.
  - The other 30 are application logic, and move into the Worker: search
    index refresh, notifications, artwork, and release rules. They are
    listed per table in `workers/api/schema/user-tables.json`.
  - One CHECK reads today's date (a release date at most a year ahead), so
    the Worker enforces it too.
- **Not copied.**
  - `media.search_documents.search_vector`, a tsvector column; search moves
    to the Worker.
  - The trigram indexes.

## Copying the user data

The export holds personal data: emails and password hashes. Keep it out of
the repository, and delete it once it has been loaded.

```sh
cd workers/api
npm run export-sql            # the read-only export; run it in the Supabase SQL editor or MCP, save the result
npm run import -- --from <saved result>            # into the remote D1 (--local for wrangler dev)
npm run verify -- --print-pg-sql                   # the read-only checksum query; run it the same way
npm run verify -- --pg <saved checksums>           # every table's SHA-256 in D1 against Postgres's
```

**What the import does:**

- It checks every value first: type, NOT NULL, timestamp form, and JSON.
- It replaces the user tables and sign-in tables in one D1 import, which
  applies all of it or none.
- Tables load parents first. D1's remote import checks foreign keys row by
  row; it doesn't honour `PRAGMA defer_foreign_keys`. So the columns that
  close the two cycles (`owner_creator_account_id` on artists and media
  assets) and `media.submission_items.replaces_item_id` are loaded as NULL,
  then filled in once every row exists. Each row's `updated_at` is put back
  after that update, so the trigger's stamp doesn't change the data.

**How the sign-in accounts carry over:**

- Supabase's email identity becomes a `credential` account, holding the
  existing bcrypt hash. The Worker accepts those hashes, and new passwords
  get Better Auth's own hash.
- A Google identity becomes a `google` account, keyed by Google's subject id.
- Sessions aren't copied. Everyone signs in again once, at the cutover.

## Sign-in (`workers/api`, Better Auth)

- **Endpoints.** Everything is under `/auth`: `sign-up/email`,
  `sign-in/email`, `sign-in/social`, `get-session`, `sign-out`,
  `request-password-reset`, `reset-password`, `change-password`,
  `change-email` and `update-user`.
- **Accounts.**
  - Users keep their Supabase ids.
  - The passwords carried over are bcrypt hashes, checked as they are; new
    ones get Better Auth's scrypt hash.
  - Email sign-up needs the confirmation email.
  - Google joins an existing account with the same verified email, as
    Supabase did.
- **Sessions.** They last 30 days and are renewed daily while used. The web
  apps use the session cookie (`copticvine.ca` is same-site with
  `api.copticvine.ca`); the native apps use the Expo plugin's stored session,
  or `Authorization: Bearer`.
- **Abuse protection.**
  - Rate limits are kept in D1 (`"auth.rate_limits"`, migration 0008), per
    address.
  - CORS and redirects only for the origins in `TRUSTED_ORIGINS`.
- **The D1 connector** (`src/auth/adapter.ts`). It builds every name with
  `t()` and `col()`, and stores dates in the user data's timestamp form. For
  text matching it uses `instr`/`substr` rather than LIKE, which keeps clear
  of D1's 50-byte pattern limit.
- **Tests.** `npm test` runs each flow end to end on the real tables in
  SQLite, with the emails kept in an outbox.
- **Locally.** `npm run dev` serves on `http://localhost:8790` against the
  local D1, with the emails kept in memory. It reads `.dev.vars`, made from
  `.dev.vars.example`.

**Before the cutover, Pierre:**

1. **Email.** In the Cloudflare dashboard, go to Compute > Email Service >
   Email Sending > Onboard Domain and pick `copticvine.ca`. The DNS records
   are added for you. Sign-in sends from `no-reply@copticvine.ca`.
2. **Google.** In Google Cloud, open the web OAuth client
   (`42138677998-dnc8…`). Add these authorized redirect URIs:
   - `https://api.copticvine.ca/auth/callback/google`
   - `http://localhost:8790/auth/callback/google`, to try it locally

   Then, in `workers/api`, run `npx wrangler secret put GOOGLE_CLIENT_SECRET`.
   For local runs, put the secret in `.dev.vars` too.
3. **At the cutover:**
   - `openssl rand -base64 32 | npx wrangler secret put BETTER_AUTH_SECRET`
   - then `npm run deploy` in `workers/api`

**Why it isn't live yet.** Until the cutover, a sign-up or password reset
made here would be wiped by the final import, and the apps still sign in with
Supabase.
